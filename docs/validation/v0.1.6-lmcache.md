# v0.1.6：LMCache 分层缓存验收

本轮只在独立容器内测试，未替换原服务或发布镜像。固定 vLLM 0.30.0 SM75 候选、torch 2.13.0+cu129、LMCache 0.5.5 cu129 与本地 packed4D 布局修复。运行说明见 [LMCache 使用说明](../lmcache.md)。

## 发现并修复的问题

1. 原始 0.5.5 不识别混合模型的 4D 子页布局。Qwen3.8-27B、TP4、FP8 KV 的 8K 冷请求正确；清空 GPU 前缀后，CPU 命中 7840 tokens 却输出乱码并达到 128-token 长度上限。这是保留的失败证据，不能将命中计数当成正确性结论。
2. 原样回移未合并的 PR #4731 后，真实启动被几何校验拒绝。vLLM 0.30 注册视图始终使用 `[B,H,N,C]` 逻辑轴，NHD/HND 表示物理步长；实测原始 shape `[4067,1,32,512]`、stride `[16384,512,512,1]`、hint NHD。补丁此前误把 head 轴 1 当 token 数。
3. 最终适配根据真实 spec 核对逻辑视图，再以元数据置换到物理顺序，保留严格连续性、字节数、整除和边界检查。83 个逻辑块各包含 49 个 32-token 内核页，转换后仍是同一块存储。旧 5D、MLA、Mamba 规则及 hybrid 分发条件不变。
4. CuPy cuda13x 与 cuda12x 同时存在会覆盖相同文件；安装器显式移除冲突所有者再安装固定 cuda12x。二进制下载校验 SHA，缺失依赖按锁文件安装，不替换推理基座；发现现有依赖不满足要求时先失败。
5. 启动/停止竞态可能使已停止缓存的过期健康响应继续启动模型。增加实例所有权复核、native 启停锁与等待清理，确保旧实例的回调不能删除或接管新实例。

补丁的精确上游 head、本地改动、前后 SHA 和许可证见 [来源记录](../../ultra/source/lmcache/patches/packed4d-provenance.json)。上游 PR 状态仍为 open/unmerged；本地适配不能称为逐字采用的上游稳定修复。

## 第一阶段：wheel＋overlay 模型与布局验收

**8/8 通过**。使用 Qwen3.8-27B-FP8、四张 T10、TP4、FP16 计算、FP8 KV；每卡 GPU KV 显式 1 GiB、整个 CPU L1 2 GiB、chunk 1568、预填充批次 2048、并发上限 4、模型长度上限 16384。测试请求 A 为 8192 tokens，分叉 B 为 8191 tokens；关闭投机、显存休眠及 expandable_segments。服务和引擎参数直接由候选 `lmcachePlan(profile)` 生成，使用最终补丁的新布局隔离目录。

| 请求阶段 | 外部命中 tokens | 回答正确 | 与对应冷算完整 token hash |
| --- | ---: | --- | --- |
| A 冷算 | 0 | 通过 | 基准 A |
| 仅清 GPU，CPU L1 恢复 A | 7840 | 通过 | 完全相同 |
| 清 GPU 与 L1，磁盘恢复 A | 7840 | 通过 | 完全相同 |
| 同提示改 cache salt | 0 | 通过 | 完全相同 |
| B 独立 salt 冷算 | 0 | 通过 | 基准 B |
| 共享前缀，从磁盘恢复 B | 7840 | 通过 | 完全相同 |
| 再从磁盘恢复 A | 7840 | 通过 | 完全相同 |
| 完整停止并重启引擎与 MP，磁盘恢复 A | 7840 | 通过 | 完全相同 |

所有请求的 GPU 前缀命中增量为 0。日志直接记录 CPU 恢复为 `24 L1, 0 L2`，首次磁盘、分叉 B、恢复 A 和服务重启后的恢复均为 `0 L1, 24 L2`，之后四个 rank 各恢复 7840 tokens。GPU 前缀与 CPU L1 均已清，唯一 L2 为 FSL2Adapter，未开启 P2P；重启保留同一目录。没有记录独立文件系统读取字节计数，不把这些日志当作物理磁盘 I/O 基准。A 的 50-token 输出 SHA 为 `d6b5d295d6d23ebadb2ced13822762b0a080f2a8e150d4c67975b82a132482de`；B 的 SHA 为 `24811f5bcb83ed5982a238d8519c2976af7eddfd5f366e4dc6c432a65b4ea0b4`。

单请求功能样本中，A 的首 token 时间为冷算 6.766 s、CPU 恢复 0.374 s、首次磁盘恢复 0.655 s；未做统计性性能基准，不能把这些数字推广为吞吐量或物理盘性能结论。

实际 `ManagedLMCache` 完成两轮启动、真实 healthy 响应、并发重复停止，两个进程均退出、端口释放。0.25 GiB CPU 配额也被实际解析为 268435456 bytes。最终安装主体完成实装与幂等补丁检查，后加的旧包升级入口另外在真实原始 0.5.4 distribution 上验证，最终安装器只读计划也通过。

测试结束，GPU 与 CPU 独立容器均已停止，四卡为 0 MiB / P8 / 0% 使用率；原开发容器保持此前停止状态。磁盘证据与测试数据保留，未替换生产服务。

## 第二阶段：完整 Ultra 镜像复验

2026-09-23，完整镜像 `6c550dc42f8659d357a92b7907289771870f3d01536a33a1cafc53517f9033d1` 通过实际 Node 管理入口重跑上述八项：**8/8 全部通过**，包括同时停止引擎与MP后从磁盘恢复。此轮直接使用镜像内安装包和本地布局补丁，没有覆盖注入vLLM wheel。

配置保持TP4、FP8目标/KV、GPU1 GiB/卡、CPU2 GiB总额、chunk1568、max16K、seq4；batch改用推荐3135，Marlin归约开关0，关闭投机、expandable_segments及原生CPU连接器。A/B输出哈希与第一阶段相同，所有外部回读命中7840 tokens且GPU前缀命中增量0。新日志明确CPU为24 L1/0 L2，四次磁盘恢复为0 L1/24 L2。

单次功能样本TTFT：冷算6.793秒、CPU恢复0.380秒、首次磁盘恢复0.660秒、进程重启后的磁盘恢复1.381秒。它们不是多轮吞吐基准，也未清OS页缓存。真实受管停止确认引擎8000、MP5555和HTTP9000三个端口均关闭；停止独立容器后显存已释放，再开始下一组GPU测试。完整结果见[新完整镜像报告](v0.1.6-full-images.md)及机器记录的 `fullImageAcceptance`。

## 边界

- 第一阶段为wheel＋overlay隔离验收；第二阶段已完成官方固定基座的完整Ultra构建及上述整模型复验。两阶段配置和证据分别保留。
- 文本、target-only 路径；未验收 DFlash/MTP 同时启用、显存 sleep/wake、图片/视频 KV、跨主机或远程存储。
- 混合 GDN 页不使用 CacheBlend/CacheGen。确定性短任务的完整 token hash 是本轮观测结果，不能推广成任意长请求逐 token 恒等的保证。
- `fs` 无硬配额，正常重启读回不等于断电持久性；L2 文件读可能由 OS 页缓存服务，不用于声称物理磁盘性能。
- LMCache 是前缀复用层，CPU＋磁盘 GiB 不会成为活动 GPU 注意力容量。LMCache组合未做百万token推理；target-only最大上下文的独立结果另见完整镜像报告。
- 测试基座保留此前已记录的部分包元数据依赖差异（包括 SM75 选择的 FlashInfer）；不靠自动升级 torch/CUDA/vLLM 来隐藏这些差异。

完整阶段结果、测试日志哈希与源码指纹见 [机器可读记录](v0.1.6-lmcache-results.json)。此前 [v0.1.6 推理验证](v0.1.6.md)、[Harness 验证](v0.1.6-harness.md) 和 [长上下文配置验证](v0.1.6-context.md) 的边界继续保留。
