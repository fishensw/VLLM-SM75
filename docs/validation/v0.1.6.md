## 本轮 GPU 环境及对照条件

4× Tesla T10 16 GiB（SM75），独立测试容器，TP4；目标模型为本地 `Qwen/Qwen3.8-27B-FP8`。最大上下文 16384、最大并发 4、批次 token 上限 2048；FlashInfer、FP8 E4M3 KV（启动 block size 参数 32，混合 GDN 在运行时对齐为 1664 tokens）、FlashQLA-SM75 GDN、CPU KV offload 512 MiB、DFlash2 draft7、FULL_AND_PIECEWISE 图捕获 8。测试接口仅绑定容器 loopback，使用临时随机 API key。

短请求原始 BF16 smoke 计数：13 次 draft、86 个 draft tokens、56 个 accepted tokens，token 接受率 65.12%。关闭推测解码后计数不增加。短句完成长度仅 4/5/12 tokens，这不是日常聊天吞吐或长输出接受率基准。

公开对照草稿来源：[nerkyor DFlash2 checkpoint](https://huggingface.co/nerkyor/Qwen3.8-27B-EfficientThink-Uncensored-K3-Opus5-Grok4.6-GPT5.6Sol-SFT-SimPO-DFlash2/tree/882e1af3b8f5844f3b3163b132e343c06e91908f/FP8/DFlash2-FP8)。固定 revision `882e1af3b8f5844f3b3163b132e343c06e91908f`；FP8 模型 SHA256 `1f3636a32d866f8ebc7f422d63f9247126ebb6d2566d3e0da327d81dd8fa25d1`。QKV 与 FC 保留 BF16，20 个 MLP/o_proj 张量为 FP8，因此 context-KV 修复不能直接证明这个 checkpoint 的 MLP 问题已消除。

同权重控制模型在 CPU 上将 20 个 FP8 张量乘各自 FP32 scale 后转为 BF16，移除量化配置与对应 scale，保留其余 61 个 BF16 张量。共 81 张量，模型 SHA256 `2a38a25dc151e0c3d75e7cb871abf4d384a48ae2e671d8fb1937d52d1be451d5`。它与原始 incoai BF16 草稿不是同一个对照组。

## 复测入口

在已启动、无其他流量的测试服务上设置 `VLLM_API_KEY`，然后运行：

```bash
python tools/validate-sm75-serving.py --base-url http://127.0.0.1:8160 --output smoke.json
python tools/benchmark-dflash-serving.py --base-url http://127.0.0.1:8160 --label fp8-draft --output fp8-long.json
```

更换为同权重 BF16 草稿后，使用相同服务配置、相同工具与新的输出文件名。长输出工具固定三个提示词、两轮串行请求、temperature=0、seed=0、max_tokens=256，并保留逐条请求、实际输出、计数差值与参数指纹。吞吐为 completion tokens / 请求总耗时，包含预填充和 HTTP 时间，不是纯 decode 指标。第二轮可能命中前缀缓存，应与另一组的第二轮比较。

GPU 数值回归：

```bash
SM75_DFLASH_FP8_CHECKPOINT=/path/to/draft/model.safetensors \
python -m pytest tests/model_executor/test_dflash_quantization_gpu.py tests/model_executor/test_v030_firefly_gpu.py -q -s
```

未设置 checkpoint 时，真实权重用例会明确跳过。Windows CPU 回归也不能替代这些 CUDA 用例。全新官方基座镜像、最大 262K 上下文、完整模型 AWQ/MoE/多模态与实机休眠恢复未作为本轮已通过事项。

## 输出一致性边界

修复前自动 Humming 与强制 Marlin 的请求指纹完全一致，但六条长输出仅两条逐 token 相同（代码提示词两轮一致；英文首次差异在第 12 个 token，中文在第 102 个）。FP8 Marlin 与同权重 BF16 的长输出也仅两条相同。因此长输出逐 token 等价性不能列为通过，短句 smoke 的一致性结果不能扩大解释。

[v0.30 推测解码文档](https://docs.vllm.ai/en/v0.30.0/features/speculative_decoding/#lossless-guarantees-of-speculative-decoding) 明确说明浮点精度和 batch 变化可能造成输出差异；这为现象提供了合理解释，不能单凭文档排除本实现的问题。官方 [batch invariance 硬件要求](https://docs.vllm.ai/en/v0.30.0/features/batch_invariance/#hardware-requirements) 为 NVIDIA compute capability 8.0+，SM75 不在该范围。最终版本另行执行同一服务开关推测解码的概率诊断，结果如下。


最终自动 Marlin 的同服务诊断包含 6 次有效 logprobs 请求，三组提示词各生成 256 tokens；请求参数、输入 token、系统指纹和首个分歧之前的输出前缀均一致。**三组长输出逐 token 完全一致性为 0/3，不通过。**

| 提示词 | 首个不同 token（从 1 开始） | 关闭推测时 top-2 logprob 差 | 开启推测时 top-2 logprob 差 |
|---|---:|---:|---:|
| 英文说明 | 12 | 0.015625 | 0.015625 |
| 中文说明 | 30 | 0.031250 | 0 |
| Python 代码 | 197 | 0.031250 | 0 |

两种模式在分歧处均选择自身 top-1；靠近并列的排名发生交换，支持浮点数值/批次敏感性的解释，但不能据此排除所有实现问题。诊断结束后已恢复推测开关。短输出一致、接受率恢复和长输出精确等价是不同的验收项。

## FP8 草稿修复前后及同权重对照

每组均使用三个相同合成提示词 × 两轮串行请求，共 1536 个输出 tokens。所有请求都达到 256-token 上限；接受率为 accepted draft tokens / drafted tokens。以下吞吐包含预填充与 HTTP，不代表通用生产负载性能。

| 草稿与选择方式 | 接受 / 草稿 tokens | 接受率 | 输出吞吐（tokens/s） |
|---|---:|---:|---:|
| FP8，修复前自动 Humming | 0 / 10710 | 0% | 23.34 |
| FP8，显式 Marlin | 902 / 4410 | 20.45% | 55.73 |
| 同权重 BF16，自动 | 912 / 4368 | 20.88% | 55.22 |
| FP8，修复后自动 Marlin | 918 / 4326 | 21.22% | 56.80 |

显式 Marlin 组使用全局 `--linear-backend marlin`，因此也会影响目标模型选核；它是诊断对照。修复前/后自动组与同权重 BF16 组均使用 `auto`，修复前后比较保持目标模型的自动选择条件一致。

最终结果证明该公开 checkpoint 在本轮配置下的零接受率问题已被 SM75 Humming 范围保护消除，性能接近同权重 BF16 控制组。测试规模有限，不把 21.22% 宣称为其他草稿或模型的预期接受率。

## 长上下文与 CPU KV

8192 / 16000 token 的精确 token-ID 输入各运行两次，读取开头、中间、末尾三个随机记录并自然停止。四次均通过；同一长度的重复输出 token 哈希完全一致，无抢占。重复请求分别观测到 4992 / 13312 个 GPU 前缀缓存命中。首次请求分别记录 CPU KV 写入 447086592 / 719716352 bytes；累计写入量不代表缓存驻留量，也不证明 CPU 回读。

CPU KV 清缓存回读：在本轮 DFlash 配置下，512 MiB 与 2 GiB 两次补测都未测到 CPU-to-GPU bytes，不能列为通过。临时元信息日志确认 CPU 有 30 个可淘汰的已完成块、容量 126 块、无挂起写入；全注意力四组均命中，GDN 十组仅保存 4992-token 边界，草稿滑窗仅保存块索引 5–8。查找收缩到 GDN 的 4992-token 边界后，草稿缺少该处需要的更早窗口，最终跨组共同前缀为 0，安全重算。两次重复输出仍与首次一致。这是已观测的联合缓存复用限制，不是缓存被重置清空，也不是容量不足；不能靠移除窗口校验来强行制造命中。v0.30 默认不挂载 `/reset_prefix_cache`；需要在仅供测试的服务启动时设置 `VLLM_SERVER_DEV_MODE=1`。第一次未启用该开关的补测返回 404，原始失败记录保留。普通重复生成不需要启用开发接口。另将预填充预算降到 1664 的单因素对照结果相同，GDN 状态仍为 4992、共同前缀仍为 0，因此没有将这个调参方案描述为修复。临时日志探针已按原始 SHA256 恢复；未对外部缓存的安全匹配条件作改动。

仅主模型对照（完全移除启动时的 speculative config，TP4 / FP8 KV / GDN / 2 GiB CPU / 2048 预填充预算保持）通过：两次 8192-token 三位置检索均正确、自然停止；清空 GPU 后读回 **410845184 bytes（391.81 MiB）**，GPU 前缀命中计数为 0，确认实际使用 CPU 层。首 token 时间 6.490 → 0.353 秒，总耗时 8.336 → 2.185 秒，两次输出 token 哈希均为 `d6b5d295d6d23ebadb2ced13822762b0a080f2a8e150d4c67975b82a132482de`。这是基础回读的控制验证，不能替代上述 DFlash 组合的未通过结果。
