## 构建期间发现并修复的问题

第一轮 `46ebafa` 完整镜像中，ultra 通过 16 项；标准版开启 `/monitor` 后，131072 输入＋512 输出检索正确、输出长度正确，但输出 token 哈希未通过原基线。该失败保留，未放宽判定或替换基线。

两次记录的编译因素仅 `VLLM_MONITOR` 不同。看板开关不影响计算图，却导致新的编译缓存目录。修复将该因素规范为原 monitor-off 缓存签名，同时保留实际监控开关的读取值。单元测试 3 项通过；两份重新构建的镜像内均验证：监控 getter 正常切换，编译因素保持一致。

随后在标准版保持 `VLLM_MONITOR=1` 的条件下重新执行所有用例，两版 22 项均与原基线的输入、输出 token 哈希一致。此结论适用于兼容编译缓存条件；不据此宣称不同冷编译产物已实现普遍逐 token 一致。

## GPU 功能验收

4× Tesla T10 16 GiB，27B FP8＋DFlash2，TP4；`NVCC_THREADS=1`，独立数据目录和隔离的兼容编译缓存。

- 标准版：8K 检索两次；131072 / 261632 输入各连续输出 512 tokens、每档两次。运行中关闭与开启投机解码后均实际生成成功，最后恢复原开关状态。
- ultra：8K / 32K / 64K / 131072 / 262016 输入检索并自然停止，每档两次；262K 后回测 64K 两次；131072 / 261632 输入各连续输出 512 tokens、每档两次。
- 两版覆盖 262144 总上下文预算，检索内容与输出长度符合契约，重复输出及原基线 token 哈希一致；观测到前缀缓存命中与 CPU KV 实际读回。
- ultra 另通过 greedy 重复、自然停止、JSON Schema、工具调用往返（合成工具结果）、控制台/DSH 启动检查。短提示词前缀冒烟本身没有证明缓存命中，命中证据来自长上下文请求。
- DSH 以 UID/GID 1000、零有效 capabilities 运行，凭据隔离与配置符号链接防护检查通过。首次凭据生成、旧凭据保留、会话恢复及已保存路径保留由镜像内控制台测试覆盖；未对整套生产数据库执行升级迁移演练。
- 标准版请求结束后四卡均进入 P8，模型各卡仍占约 15277 MiB，功耗约 11–14 W/卡。本次为快速验收，使用空闲 1 秒、确认 0 秒；不是默认等待时间或其他硬件功耗承诺。

首次 262K 边界请求仍有 2 次 KV 抢占，重复请求无抢占；与历史现象一致。此处为功能验收，不是无缓存性能基准，不将重复命中的耗时换算为新提速成果。逐项输入、哈希、耗时和计数见 [机器可读结果](2026-09-18-final-review.json)。
