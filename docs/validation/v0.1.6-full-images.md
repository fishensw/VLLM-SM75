# v0.1.6 完整镜像验收与发布限制

标准版和 Ultra 完整镜像已构建并完成本轮四 T10 验收：两版 DFlash2 性能与 256K 持续生成、Ultra 浏览器和自动 P-State、分层缓存八项复验。标准版 128K decode 回归与跨镜像 token 等价门禁仍未通过，保持待发布候选。机器可读证据见 [结构化结果](v0.1.6-full-images-results.json)。

## 构建与产物

本地正式 Ultra 镜像由已验收的完整镜像派生，后续界面层保留现有 SM75 主界面，并整合 DSH、Watcher、中文提示与受工作区约束的原生目录列表工具。早期界面补充记录为 185 项 Node 回归中 178 通过、7 项平台或环境相关跳过，另完成目录边界与无 GPU 浏览器检查。当前统一界面的最终证据以 [工作台整合验收](v0.1.6-workbench-integration.md) 和 [统一 UI 结构化结果](v0.1.6-unified-ui-results.json) 为准。推理二进制与模型运行层沿用已测镜像；正式标签没有单独重跑 GPU 性能，以下性能表对应原完整镜像。

每个归档约 17 GiB，均包含完整基础层。Docker 格式标准版 98 层、17,812,275,200 bytes；Ultra 109 层、18,161,766,400 bytes。没有省略父层，也不依赖正式旧镜像才能导入。完整 OCI manifest、门禁和逐文件运行时信息保存在结构化结果中。产物只保存在本次测试机的专用构建目录，尚未上传公共仓库。

复用完整归档时，在独立部署机校验同目录的 `SHA256SUMS` 后导入所需 Docker 格式归档。OCI 和 Docker 格式是两套完整产物，选择合适格式即可；不需要将二者都导入。命令中的 Docker 应指向准备部署的独立实例，不指向生产 Unraid 的正式 daemon。

```bash
sha256sum -c SHA256SUMS
docker load -i v0.1.6-rc1.docker.tar
# 已按主 README 设置模型、缓存、密钥和 NVAPI 路径时：
IMAGE=local/vllm-sm75:v0.1.6-rc1 VARIANT=base MAX_MODEL_LEN=32768 bash docker/run.sh
# ultra 单独导入和启动；两版不要同时占用同组 GPU：
# docker load -i v0.1.6-ultra-rc1.docker.tar
# IMAGE=local/vllm-sm75:v0.1.6-ultra-rc1 EDITION=ultra bash docker/run.sh
```

构建使用独立 BuildKit 0.29.0、8 GiB RAM、2 CPU、MAX_JOBS=1；导入使用已授权的独立 Docker、4 GiB RAM、2 CPU。导入后 daemon 降为 2 GiB，模型容器另限 24 GiB / 8 CPU。大层经 OCI 目录导出及受限流式归档处理，不通过正式 daemon 导出/导入。

## DFlash2 性能契约

对照正式 `IP53_VLLM-Qwen3.8-27B-FP8-SM75-GDN-ultra` 的运行参数：同一 Qwen3.8-27B-FP8 目标和 DFlash2 草稿文件，TP4、FP16、draft7、FP8 E4M3 KV、max-model-len262144、seq4、batch8192、GPU KV3,288,334,336 bytes/卡、CPU KV8 GiB/组、FlashInfer、GDN FlashQLA prefill＋Triton decode、graph size8。目录名称不代表重新确认过 checkpoint 的官方名称；目标配置架构为 `Qwen3_5ForConditionalGeneration`。

每种长度预热后取三次中位数。性能请求为固定 token 输入、三位置检索和持续续写、512-token 输出，独立 cache salt，要求完整输出、检索正确、缓存命中 0 和抢占 0。prefill 为输入 token / TTFT，包含请求开销；decode 扣除首批 token 数，按首批至最后 token 的窗口计时，不包含尾部 usage 等待。不同生成内容和草稿接受率会影响结果。

| 镜像 | 输入 | Prefill tok/s | Decode tok/s | TTFT 秒 | 草稿接受率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| v0.1.5 Ultra 基线 | 8192 | 1271.71 | 62.74 | 6.44 | 25.04% |
| v0.1.6 标准版 | 8192 | 1282.27 | 65.78 | 6.39 | 27.35% |
| v0.1.6 Ultra | 8192 | 1281.34 | 60.49 | 6.39 | 23.74% |
| v0.1.5 Ultra 基线 | 32768 | 1203.77 | 58.84 | 27.22 | 23.69% |
| v0.1.6 标准版 | 32768 | 1209.02 | 64.46 | 27.10 | 27.43% |
| v0.1.6 Ultra | 32768 | 1207.62 | 63.47 | 27.13 | 26.66% |
| v0.1.5 Ultra 基线 | 131072 | 976.08 | 59.85 | 134.28 | 27.52% |
| v0.1.6 标准版 | 131072 | 977.80 | 53.01 | 134.05 | 23.37% |
| v0.1.6 Ultra | 131072 | 978.08 | 58.73 | 134.01 | 26.50% |

三种镜像的各 9 次性能样本均有效。Ultra 各长度对旧版均在 5%吞吐容差内，但三种长度的输出 token 哈希均不同；相对标准版，Ultra 的 8K decode 下降 8.04%、128K 反而更快，接受率和续写内容也不同，不能直接解释为固定面板开销。

标准版 128K decode 比基线低 **11.43%**，超过 5%容差；三种长度的跨版本输出 token 哈希也不同，因此严格回归门禁失败。两版各自在同一长度的三次运行内输出稳定，不代表跨版本等价。128K 草稿步骤/解码窗口约从 20.62 降至 20.23 次/秒，接受率同时下降；这些观察不能单独证明回归根因。

基线镜像 ID 为 `sha256:dbbf2ad146e2b8b1e1acd7a85754108e978f32a54526842de99b554ae16196a2`。本轮契约与旧 v0.1.4 历史性能表不同，不能用旧表 179/166 tok/s 计算本轮回归。工具摘要：benchmark `40006f79dcc5f8151b9f1bc87d624a0b69aa92d46531caa040231923e8aaa2cc`；协议 `022328f1533568eeed78b0da139a5ef3dd27c881957536d19cf6ea807f9053a0`。

## DFlash2 短草稿配置对照

完整标准版另测 draft3、graph size4、target/draft max163840，同样保留每卡 3.06 GiB GPU KV、CPU8 GiB、seq4、batch8192。128K 输入＋512 输出预热后三次均有效、输出一致；中位 prefill **979.89 tok/s**、decode **52.85 tok/s**、接受率 **49.44%**。接受率高于 draft7，但每轮最多接受的 token 数也减少，不能仅用百分比推断加速；实际 decode 未改善。

最初保持 max262144 时，启动检查报告需要 3.8 GiB KV、只有 3.06 GiB，因此未启动；第一次降长度只修改目标，草稿上限仍大于目标，验证直接拒绝。最终同时调低两者后才完成测量。长度上限、草稿数和 graph size 都有变化，不作为单变量因果试验，也不将 draft3 推荐为现有 256K 模板的替代。

## 256K 持续生成与 CPU KV

| v0.1.5 Ultra 冷请求 | 内容及 512 输出完成 | 339.71 | 2 | 860,094,464 bytes |
| v0.1.5 Ultra 重复请求 | 内容完成，但与冷请求续写 token 不同 | 2.98 | 0 | 430,047,232 bytes |

| v0.1.6 Ultra 重复请求 | 通过，与标准版 token 一致 | 335.39 | 0 | 未记录回读 |

两版共四次 SHA256 为 `b8fa10193fc5d28b05796c6748cf4238da8317253d10f9bad5b587aa2b107c27`。CPU store 累计增加不等于可恢复命中；本配置重复请求实际重算，不能宣称 CPU KV 改善了热前缀延迟。8K 自然停止检索两次通过，且与基线答案一致。基线另外完成 8192/32768/131072/262016 输入的自然停止 8 次检查，但其 256K 持续续写严格重复性失败。

## Ultra 面板、Harness 和 P-State

完整 Ultra 实际 Node 入口验收通过：浏览器登录，1440px 桌面和 420px 窄屏控件均可用；硬件监控读到真实 T10。Harness 0.1.7-alpha.2 的资源与双向 WebSocket 正常，首次提示关闭后进入[实际工作台](../assets/v0.1.6-harness-workspace.png)。

浏览器没有 JavaScript 异常。首次完整检查没有失败 HTTP 响应；关闭 DFlash 引擎后的补充工作台检查中，该停止配置的 metrics/spec 轮询返回 400，记录为离线配置的预期响应。新完整镜像本轮检查的是管理、页面和连接；更广的工具/迁移验收另见[Harness专项记录](v0.1.6-harness.md)。

P-State 真实切换：通过面板手动 P8 接口触发，未等待 1800 秒自动空闲计时。四卡从 P0 进入 P8，每卡已用显存始终为 15,377 MiB；随后 256-token 生成成功，用时 4.57 秒（整个请求耗时，不是唤醒 TTFT），监管器回到 active，GPU 恢复工作频率。切换前瞬时功率 38.94–44.23 W/卡，首次 P8 采样 19.39–24.95 W/卡；这是短时功能采样，不能当作长时间平均功耗或其他负载的节能承诺。高态值 16 表示恢复驱动控制，不是硬件 P16。

补充自动计时验收通过：通过正常 Ultra 管理入口启动 AWQ 配置，仅用短请求验证。idle=10 秒、confirm=5 秒、poll=1 秒，不调用手动 P8 接口；约 16.35 秒后四卡自动进入 P8，显存变化均不超过 8 MiB。随后请求完成 256 tokens，四卡均恢复非 P8 工作频率，监管器回到 active；请求总耗时 5.32 秒，不作为唤醒 TTFT。主 DFlash2 性能配置仍为 idle=1800 秒，此短时功能测试不等于实测等待 1800 秒，也不用于跨配置性能对比。

## 完整镜像 LMCache 回读

实际 Ultra 管理入口启动目标模型及 LMCache MP，关闭 DFlash/MTP、原生 CPU 连接器、expandable_segments；GPU KV1 GiB/卡、CPU L1 共 2 GiB、chunk1568、batch3135、max16K、Marlin 归约 0。八项检查全部通过：冷算、CPU 恢复、磁盘恢复、salt 隔离、分叉 B 冷算、共享前缀磁盘恢复 B、恢复 A、引擎及 MP 重启后磁盘恢复 A。

CPU/磁盘回读均命中 7840 tokens，三位置检索及输出 token 与对应冷算相同，GPU 前缀命中增量 0。服务日志分别记录 24 L1/0 L2 与 0 L1/24 L2，四个 rank 实际恢复 7840 tokens。单次 TTFT 冷算 6.793 秒、CPU0.380 秒、首次磁盘 0.660 秒、重启磁盘 1.381 秒；未清 OS 页缓存，不作为物理盘或统计性能基准。两个受管停止周期均确认全部服务端口关闭。详见[分阶段验收](v0.1.6-lmcache.md#第二阶段完整-ultra-镜像复验)。

## 构建中发现并修复的问题

- 官方固定 cu129 基座实际包含 Torch2.14/cu130，与 vLLM 和 torchvision 的 Torch2.13 依赖不一致；显式恢复 Torch2.13.0+cu129、Triton3.7.1 以及 cuda-python/cuda-bindings12.9.7，再编译扩展。
- cu13 的 cuDNN、cuSPARSELt、NCCL、NVSHMEM 覆盖了同名 cu12 动态库；移除冲突分发、强制重装 cu12，并逐文件核对 wheel RECORD 哈希。没有取消 ABI 门禁。
- 无 GPU 构建中的 12 个模拟设备选择测试未指定 DeviceConfig；修正 fixture 后 126 项全部通过，保留 SM75 拒绝/回退和 SM80 保留断言。
- 无 GPU 构建不能导入依赖宿主 libcuda 的 Mooncake；可选安装明确使用 headless 模式，仅将驱动连接器门禁移至真实 GPU 预检和每次启用前的探针，原生扩展 ABI 仍在构建阶段验证。
- 单 tarball 导出曾触发本次 worker 的 8GiB 硬限制，正式 Docker 未重启；改用低内存 OCI 目录导出和流式归档后成功。独立 Docker 导入期间 oom/oom_kill 均为 0。
- Unraid 第二 Docker 需`DOCKER_RAMDISK=true`和独立网络命名空间。首次共享网络命名空间时`--bridge=none`删除 docker0，已按启动前配置恢复；后续独立实例只启用自己的 loopback，正式 daemon 没有重启。

## 范围与发布状态

目前不能标记“全部性能无回归”或“DFlash2 长请求逐 token 等价”。issue #13 原始 checkpoint 尚未完全确认；旧覆盖层 LMCache/Harness 功能证据与本次完整镜像结果分别保留。当前验收入口为 Ultra 单容器/native 方式；旧外部 Docker profile 路径仍带 v015 标签限制，不在本轮支持范围。

验收后，本次 GPU 容器、BuildKit worker 和临时独立 Docker 均已停止，四卡显存释放。随后在正式 Docker 中安装本地 `vllm-sm75:v0.1.6-ultra` 镜像，并将指定四份 Unraid 模板和容器定义切换到该镜像；Ultra 管理容器随后恢复运行，其余三个保持未启动；模型数据挂载保持不变。四个容器由 Unraid Docker Manager 托管，图标与 WebUI 标签按模板保留。旧测试容器、旧镜像标签和非保留的 VLLM-SM75 模板已清理；未推送 GitHub 或公开镜像。验收阶段宿主记录保存在证据包的 `final-host-state.log`。
